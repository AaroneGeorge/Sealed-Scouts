# Threat model

**Version: v0, to be updated with tx evidence.**

This file says what Sealed Scouts protects, who can attack it, what stops each attack, and what is left over.
Anything that is not yet a transaction on the QoreChain testnet is described as design, not as done. When evidence
becomes a transaction hash, it goes into [PROOF.md](PROOF.md) (generated by `npm run proof`), and this file links to
it. Known limits are in [LIMITS.md](LIMITS.md). The shape of the system is in [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Network: QoreChain testnet `qorechain-diana`, EVM chain id 9800. Rollup: `sealed-scouts-1`.

## 1. Scope and assets

What we protect:

| Asset | Why it matters |
|---|---|
| Feed prices (fETH, fBTC, fUSD, and an optional real-world feed) | Apps that read them lend, mint or liquidate on them. |
| Funds of apps that read the feed | A wrong price can drain a lender. The demo lender is `ScoutLend`. |
| Operator bond (EVM, in `PriceFeed`) | The cost of posting a wrong price. |
| Scout bonds (EVM, in `PriceFeed`) | The cost of reporting far from the truth. |
| Rollup ledger balances | Scout rewards and withdrawals, kept on the rollup ledger. |
| Report secrecy until the round closes | Stops one scout copying another. |

In scope: the contracts in `contracts/`, the bots and watchtower in `packages/`, the read API and demo page in
`apps/`, and the way they use QoreChain's rollup module (`x/rdk`), its post-quantum signature rule and the EVM
precompiles `pqcVerify` and `pqcKeyStatus`.

Out of scope: QoreChain itself (consensus, the RDK's fraud proof, the precompiles), the exchanges that publish
prices, the test tokens' market value (there is none), and the user's own machine.

## 2. Actors

| Actor | What it does | What we assume about it |
|---|---|---|
| Scout | A bonded bot. Reads exchange prices, seals a report, signs a commitment, posts both to the rollup inbox. | May be dishonest or lazy. Holds its own keys. |
| Operator | Opens reports at round close, plans and submits batches, pays rewards, relays rounds to the EVM. In v1 it is also the creator, sequencer, opener and relayer. | May lie. Has a bond. Is one party (limit L6). |
| Watchtower | Replays the ledger and the rounds from chain data. Challenges a wrong median. Sends fraud proofs for a wrong ledger root. Publishes the status feed. | Anyone can run one. At least one honest one is online in the challenge window. |
| Consumer contract | Reads a price from `PriceFeed`. The demo one is `ScoutLend`. | Reads only final, fresh prices. |
| Relayer | Calls `PriceFeed.postRound` with the anchor signature. | Anyone. Holds no authority: the signature is what counts. |
| Outside attacker | Can send any transaction and read everything public. | Has no scout or operator key. |
| Quantum attacker | Holds **every classical secp256k1 private key** in the system. Holds **no ML-DSA key and no ML-KEM key**. | Can sign anything a classical key could sign. Cannot forge ML-DSA-87 signatures or open ML-KEM-1024 envelopes. |

The quantum attacker is the case this project is built for. See section 7.

## 3. Trust assumptions

We rely on all of these. If one fails, the guarantees below may not hold.

1. QoreChain consensus is honest and live.
2. ML-DSA-87 and ML-KEM-1024 hold, and so do SHA-256, SHAKE-256 and Keccak-256.
3. The chain's rule `hybrid_signature_mode: required` with `allow_classical_fallback: false` stays on. A
   classical-only transaction is then refused.
4. The precompiles `pqcVerify` and `pqcKeyStatus` answer correctly on the testnet EVM.
5. At least one honest watchtower is online within the challenge window of a round.
6. Most bonded scouts are honest. Bond size and scout count are the lever.
7. The operator's opener key is not leaked before the round closes (limit L3).
8. Public endpoints may fail. That affects liveness only. A failed read is an error, never a zero.

## 4. Trust boundaries

Each boundary says who is trusted on the far side and what crosses it.

| Boundary | What is trusted | What crosses it | Check on the way in |
|---|---|---|---|
| Chain consensus (`x/rdk`, `x/pqc`, `x/multilayer`) | Honest majority, the hybrid signature rule | Transactions, inbox posts, batches, anchors, fraud proofs | The chain refuses a transaction without an ML-DSA-87 signature. |
| Rollup inbox | Order, height and poster are stamped by the chain. Content is not trusted. | `REPORT`, `COMMIT`, `OPEN`, `REVEAL`, `JOIN` entries | `deriveRound` ignores anything malformed, off-window or ineligible, and gives a reason. |
| Off-chain opener | One key holder (the operator) can decrypt sealed reports | Plaintext prices after the commit window | Each opened report must hash to the scout's signed commitment. |
| EVM contracts (`PriceFeed`, `ScoutLend`) | The precompiles, and the creator's key as `pqcKeyStatus` reports it | Round attestations, anchor signatures, challenges, bonds | `pqcVerify` on every round. `msg.sender` is never an authority. |
| Public endpoints (REST, EVM RPC) | Nothing: liveness only | Reads | Reads are cross-checked against the chain's own commitments. |
| Our read-only API proxy and demo page | Nothing. It holds no keys. | Whitelisted GET reads, and the watchtower's feed files | GET and HEAD only, a fixed list of QoreChain REST paths, rate limited. |

The proxy exists because QoreChain REST sends no CORS headers, so a browser page cannot call it directly. It forwards
only the reads on its list, caches them for a short time and refuses everything else. It cannot sign, send or
change anything. The page calls the public EVM endpoint directly for `pqcKeyStatus` and `pqcVerify`, which allows
browser origins. A wrong answer from the proxy or the endpoint cannot make a bad round look valid to
`PriceFeed`, because the contract does its own check. It can only make the page show wrong text, and the same checks
can be repeated by hand (section 10).

## 5. Cryptographic inventory

| Algorithm | Where used | Why |
|---|---|---|
| ML-DSA-87 | Transactions (hybrid), batch anchor signatures, scout commitments (`COMMIT`), bond exit authorisation in `PriceFeed` | The chain's post-quantum signature. Public key 2,592 bytes, signature 4,627 bytes. |
| ML-DSA-44 | Ledger accounts on the rollup | Fixed by the chain's `qledger-v1` ledger. Account keys there are ML-DSA-44 only. |
| ML-KEM-1024 + AES-256-GCM (QoreSeal) | Sealing each report to the opener's registered key | Report secrecy until the round closes. A sealed report is about 1,850 bytes. |
| SHA-256 | Report commitment | Binds a report to its salt, round and scout. |
| SHAKE-256 | Inside the chain's post-quantum schemes | Used by QoreChain's libraries, not chosen by us. |
| Keccak-256 | Round hash, leaf hash, Merkle tree in `PriceFeed` | Cheap on the EVM. |
| secp256k1 (ECDSA) | The classical half of every hybrid transaction, and EVM accounts | Present everywhere, **never sufficient alone**: the chain refuses a transaction that has only this signature. |

A machine-readable inventory file for a scanner is not in the repo yet.

## 6. Attack table

"Evidence" names a test (run with `npm run test:contracts` for the Solidity ones, `npm test` for the TypeScript
ones), the red-team script, or a transaction that will be listed in [PROOF.md](PROOF.md). A row that says "pending"
has a design but no transaction on chain yet. `npm run redteam -w @sealed-scouts/attacks` replays the attacks; rows that need a live
transaction stay pending until a live run is recorded.

| # | Attack | What stops it | Evidence | What is left |
|---|---|---|---|---|
| 1 | Stolen classical keys post reports | The chain's hybrid rule refuses a transaction without an ML-DSA-87 signature. | Refused tx from `npm run redteam` (pending); PROOF.md claim list | Nothing, if assumption 3 holds. |
| 2 | Stolen classical key acts on the EVM | Contracts never trust `msg.sender`. Privileged calls (bond exit) need an ML-DSA-87 signature. | `Bonds.t.sol`: `test_exitNeedsTheOwnersKey`, `test_exitSignatureWorksOnce` | A classical key can still fund a bond or call public functions. That gives it no authority. |
| 3 | Forged batch posted to the feed | `postRound` rebuilds the anchor bytes and calls `pqcVerify` against the creator's registered key. | `PriceFeed.t.sol`: `test_oneChangedBitIsRefused`, `test_signatureFromAnotherKeyIsRefused`, `test_validAnchorIsAccepted`; live read in `npm run judge` | The creator's ML-DSA key must stay secret (section 3). |
| 4 | Replay of an old round, or another chain's anchor | A round and batch index must be above the last posted one. Chain id and rollup id are inside the signed bytes. | `PriceFeed.t.sol`: `test_replayAndOldRoundsAreRefused`; `Vectors.t.sol`: `test_anchorVectorsAndRealSignatures` | Nothing known. |
| 5 | Operator posts a wrong median | Anyone calls `challengeMedian` with all leaves. The contract checks them against `reportsRoot`, recomputes the median, slashes the operator bond (half to the caller, half locked as burned) and stores the right price. | `PriceFeed.t.sol`: `test_wrongMedianIsChallengedAndSlashed`, `test_wrongCountIsAFault`; `packages/watchtower/test/tower.test.ts`; live tx pending | Needs an honest watchtower in the window (row 17). |
| 6 | Operator posts a wrong ledger root | The chain's fraud proof (`MsgChallengeBatch`) re-runs the batch and slashes the submitter bond (1,000 QOR). | Tx in PROOF.md (pending) | The chain's proof covers the ledger only, not prices (limit L2). |
| 7 | Operator changes a report | Each opened report must hash to the scout's signed commitment. The scout's ML-DSA-87 signature covers the commitment. | `packages/core/test/commit.test.ts`; `derive.test.ts` (opening mismatch is rejected) | Nothing. A changed report simply does not count. |
| 8 | Operator skips a valid report | The scout posts `REVEAL` itself in the grace window. The skip is counted in public (`skippedByOpener`). | `derive.test.ts` (REVEAL rules); skip counter in the status feed | **No slash in v1** (limit L4). |
| 9 | Operator adds a fake report | Replay flags it. A report needs a matching signed `COMMIT` from an eligible scout. | `derive.test.ts`; `npm run watchtower -w @sealed-scouts/watchtower -- --observe` | **No slash in v1** (limit L5). Slashing an honest scout would need its own signature, so it is safe. |
| 10 | Operator reads reports early | None. Design: seal twice, so no single holder can open (stretch goal). | Not covered | **One opener is trusted** (limit L3). |
| 11 | Scout copies another scout | Reports are sealed until the round closes. Each scout uses a different set of exchanges, so copying would show. | Design; sealed posts in PROOF.md (pending) | A leaked opener key breaks this (row 10). |
| 12 | Scout waits to reveal after seeing the others | Not possible: the operator opens for all, and a scout can only add its own `REVEAL` of the same committed report. | `derive.test.ts` (reveal and open windows) | Nothing. |
| 13 | Scout reports far off | It falls outside the band and is excluded from the median. If it is beyond the slash band, anyone can call `slashOutlier` with the scout's own signed commitment. | `PriceFeed.t.sol`: `test_outlierIsSlashedWithItsOwnSignature`, `test_inBandScoutIsNotSlashable` | Live tx pending. |
| 14 | A scout is slashed without cause | `slashOutlier` needs that scout's own COMMIT signature and a leaf in the round. | `PriceFeed.t.sol`: `test_scoutCannotBeSlashedWithoutItsSignature`, `test_slashNeedsLeafInRound` | Nothing. |
| 15 | Scout front-runs with a late report | The commit window is counted in main-chain blocks, and the chain stamps each post's height. A late post is ignored. | `derive.test.ts` (window rules, `outside-commit-window`) | Nothing. |
| 16 | Majority of scouts collude | Out of scope. Bond size and the number of scouts are the only levers. | Not covered | The median follows the majority. |
| 17 | Watchtower is offline | A pending round goes final unchallenged after the window. Anyone can run a watchtower. A longer window helps. | `PriceFeed.t.sol`: `test_pendingTurnsFinalAfterWindow` | A wrong price can become final if nobody watches. |
| 18 | False challenge against an honest round | The contract recomputes the median from the leaves. An honest round cannot be slashed. | `PriceFeed.t.sol`: `test_honestRoundCannotBeChallenged`, `test_challengeNeedsTheCommittedLeaves`, `test_challengeAfterWindowIsRefused` | Nothing. |
| 19 | Consumer reads a pending or stale price | `readFinal` reverts unless the price is final and fresh. | `PriceFeed.t.sol`: `test_stalePriceReverts`; `ScoutLend.t.sol`: `test_pendingPriceRefusesBorrow`, `test_stalePriceRefusesBorrow`, `test_noPriceAtAllRefusesBorrow` | A consumer that skips `readFinal` is on its own. |
| 20 | The chain later rejects a batch | A round depends on inbox data only, not on the ledger root. | Design; `deriveRound` is a pure function of inbox entries | Rewards for that batch are delayed with the ledger. |
| 21 | Key loss or rotation | The feed reads the creator's current key from `pqcKeyStatus` on every call. An unproven key is refused. | `PriceFeed.t.sol`: `test_unprovenOperatorKeyIsRefused` | Changing a post-quantum key closes open EVM windows on the chain (chain v3.2.8). Plan for a short gap. |
| 22 | A public endpoint is down or rate limited | Retries with back-off and a fixed user agent. A failed read is an error, never a zero. | `packages/chain/test/http.test.ts`; `apps/api/test/proxy.test.ts` | Liveness only. |
| 23 | The precompile is missing (not on mainnet) | The contracts fail closed: a call reverts instead of accepting. | `PriceFeed.t.sol`: `test_failsClosedWithoutPrecompile` | Testnet only (limit L1). |
| 24 | The API proxy is used as an open relay | Fixed path list, allowed query keys only, GET and HEAD only, rate limit, short cache. | `apps/api/test/proxy.test.ts` | It can be rate limited or taken down. That is a liveness issue. |

## 7. Q-Day walk-through

### 7.1 Stolen keys

Setting: on Q-Day a quantum attacker recovers the classical secp256k1 private key of 3 of our 5 scouts. A majority
of the scouts' classical keys is now in the attacker's hands. The attacker has no ML-DSA-87 key of any scout and no
ML-KEM key.

1. **The attacker tries to post a report as one of the three scouts.** The transaction is signed with the stolen
   classical key only. The chain's rule is `hybrid_signature_mode: required`, with no classical fallback. The chain
   refuses the transaction. (Evidence: the refusal text and code from `npm run redteam`, to be recorded in PROOF.md.)
2. **The attacker tries to act on the EVM as a scout.** Bond exits need an ML-DSA-87 signature over a message
   that names the chain, the feed, the account and a nonce. A classical signature does not help.
   `msg.sender` is not an authority. (Test: `test_exitNeedsTheOwnersKey`.)
3. **The attacker makes their own account.** They register their own ML-DSA-87 key and send a valid hybrid
   transaction. That passes the chain's rule. But the account is not an eligible scout: eligibility is checked
   by `deriveRound` against the list of scouts in the deployment file. Its reports are listed as
   rejected (`not-eligible`) and never reach the median.
4. **The attacker forges a batch for the feed.** They build a round with a price of their choice and call
   `PriceFeed.postRound` with a signature. The contract rebuilds the anchor bytes, reads the creator's key from
   `pqcKeyStatus` and calls `pqcVerify`. The signature is not the creator's ML-DSA-87 signature, so `pqcVerify`
   returns false and the call reverts. One changed bit also fails. (Tests: `test_oneChangedBitIsRefused`,
   `test_signatureFromAnotherKeyIsRefused`.)
5. **The attacker reads sealed reports.** Each report is sealed with ML-KEM-1024 to the opener's key. The attacker
   does not hold it.

Result: no price changes, no bond moves, no report is forged. What the attacker still has: classical keys that sign
classical transactions, which the chain no longer accepts alone. If the attacker also got the creator's ML-DSA-87
key, steps 3 and 4 would fail open. That is assumption 2 and a real limit of any signature scheme.

For contrast, a classical oracle that trusts ECDSA reporter signatures would accept step 1. The demo page shows that
comparison on a **local simulated chain** and labels it as simulated. It is not a result from the testnet.

### 7.2 The operator lies

Setting: the operator is dishonest and posts a wrong median.

1. **Report and open.** Scouts post sealed reports and signed commitments. The operator opens them and posts one
   `OPEN` entry. Anyone can check each opened report against its commitment.
2. **Wrong median.** The operator posts a round whose median is not the median of the committed leaves. The batch
   anchor is signed, so `postRound` accepts it and the round is `Pending`.
3. **Watchtower challenge.** The watchtower derives the round from the same inbox entries with the same pure
   function. The medians differ. It calls `challengeMedian(round, leaves)` inside the challenge window (120 s in the
   demo configuration).
4. **Court recompute.** The contract checks that the leaves are sorted and hash to `reportsRoot`, recomputes the
   median and counts, and finds a fault.
5. **Slash.** The whole operator bond is slashed. Half goes to the caller and half is locked as burned. The right
   price is stored and marked corrected. `ScoutLend` reads the corrected price.

The same story for a wrong ledger root runs on the chain instead: the watchtower sends the RDK's fraud proof, the
chain re-runs the batch and slashes the submitter bond (1,000 QOR). The two are tied only by the anchor signature
(limit L2).

Evidence: contract tests `test_wrongMedianIsChallengedAndSlashed` and `test_honestRoundCannotBeChallenged`;
live transactions will be listed in [PROOF.md](PROOF.md) once they exist. Until then this walk-through is design
backed by tests, not by testnet transactions.

## 8. Privacy

| What | Visible to whom | Until when |
|---|---|---|
| Report prices | Only the opener (the operator) | Until the round closes. After that, `OPEN` (or the scout's `REVEAL`) puts the plaintext on chain, for everyone. |
| That a scout reported, and when | Everyone | Always. The poster and block height are stamped by the chain. |
| Sizes of reports and signatures | Everyone | Always. |
| Who the scouts are, their bonds, their slashes | Everyone | Always. |
| Medians, round hashes, `reportsRoot` | Everyone | Always. |

Only the report contents are hidden, and only until close. This is not an anonymity system. It stops copying
between scouts. It does not hide a scout from the operator, and the operator can read reports early (limit L3).

## 9. Limits and out of scope

The full list is in [LIMITS.md](LIMITS.md). The short version:

- Testnet only. The precompiles are not active on mainnet, so the contracts fail closed there.
- One operator runs most roles in v1. One opener can read reports early.
- Leaving a report out, or adding a fake one, is flagged but not slashed in v1.
- The chain's fraud proof covers the ledger, not prices. Price faults are judged by our EVM court.
- Not audited. Toy economics. Do not use real funds.

Out of scope: collusion of a majority of scouts, attacks on QoreChain consensus or its precompiles, attacks on
the exchanges, and anything about the value of the test tokens.

## 10. How to check each claim with no key

None of these needs a key or an account. Commands run from the repo root after `npm install`. Scripts live in the
workspaces, so use `-w`.

| Claim | Command or page | What a pass looks like |
|---|---|---|
| The latest batch's settlement receipt passes the RDK's 6 checks, a copy with one changed digit fails, and `pqcVerify` on the EVM accepts the anchor signature (and refuses one flipped bit) | `npm run judge -w @sealed-scouts/api` | `PASS` lines; exit 0. Exit 3 means part of the system is not live yet. Exit 1 is a failed check. |
| The round's hash is in the anchor's `validator_set_hash` slot, and `PriceFeed.verifyReceipt` agrees | the same command | `Round N bound into the anchor` and `PriceFeed.verifyReceipt` lines. |
| The same receipt checks work on any other live optimistic rollup | `npm run judge -w @sealed-scouts/api -- --rollup <rollup id>` | Shows the checks are real, not tuned to our rollup. |
| A round re-derives from raw inbox data, and wrong medians are flagged | `npm run watchtower -w @sealed-scouts/watchtower -- --observe --once` | The watchtower writes `feed/status.json` and `feed/rounds/<n>.json` and sends nothing. |
| The contract-side attacks are refused | `npm run test:contracts` (needs Foundry) | All tests in the table above pass. |
| The TypeScript rules (windows, commitments, eligibility) hold | `npm test` | Tests pass. |
| The attack runs against the testnet | `npm run redteam -w @sealed-scouts/attacks` | Each attack ends REFUSED. Each live run is recorded in `packages/attacks/evidence/` and listed in PROOF.md. |
| Each receipt check, in the browser | The demo page: the **Verify** tab (any rollup, six checks) or a round's page (eight) | The checks run one by one: the six receipt checks (rollup bound to its layer, batch state root, anchor on chain, creator key, chain binding, `pqcVerify`) and two that bind our round (anchor covers the round hash, `PriceFeed` accepts the receipt). A "tamper" switch changes one digit and the signature check fails. |
| Every claim with its transaction | [PROOF.md](PROOF.md), regenerate with `npm run proof -w @sealed-scouts/api` | A table of claims. A claim without a transaction says `pending`. |

To repeat the `pqcVerify` call without our page, the Verify tab prints a `curl` line that sends the same `eth_call`
to the public EVM endpoint.
